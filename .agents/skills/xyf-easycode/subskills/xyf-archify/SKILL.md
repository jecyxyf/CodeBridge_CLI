# XYF Archify

按“理解 → 执行 → 检查”完成软件框架工作。主线为：确定生成方式与分析范围 → 梳理框架内容 → 自上而下布局 → 校验配置 → 部署网页。

## 1. 理解

### 职责与数据基准

架构设计统一保存在一份项目配置中，网页围绕这份配置展示和编辑。可以读取源码作为依据，不编写、修改或测试业务代码；业务实现由同级 [xyf-code](../xyf-code/SKILL.md) 负责。任务在当前 Agent 内完成，不启动额外 Agent。

确定目标项目、本次功能范围、当前架构文件和修改范围。读取项目协作规则，沿用已有授权；优先从上下文判断，只询问确实缺少的关键信息。

已有项目使用当前配置，保留稳定 ID、用户编辑、布局及范围外内容。已知网页有未保存编辑时先处理。不能用旧快照或工具自带空框架覆盖用户内容，也不能把新目录下的空文件当作已有项目的数据基准。

### 两种生成方式

| 项目情况 | 必须采用的方式 |
|---|---|
| 空白项目，通过需求生成框架 | 先使用同级 [brainstorming](../brainstorming/SKILL.md) 技能，通过对话梳理并确认设计，再生成配置 |
| 已有代码，通过实现生成框架 | 先理解真实关系，再决定分层、模块和位置；内容严格以实际代码为依据 |

空白项目必须经过头脑风暴，不能跳过对话直接凭猜测填写。按本任务只生成框架配置的范围使用 brainstorming：梳理项目目标、功能、分层、模块及内部内容，结论写入配置；不另行编写业务代码、规格文件或实现计划，不自动提交 Git。已完成并确认的头脑风暴结论可直接沿用，不重复询问。

已有代码时，先按下面规则确定业务源码范围，再从范围内的入口、注册和配置开始，沿实际调用、数据流和读写操作追踪到执行与输出位置。区分调用者、实际执行者、数据接收或保存位置，以及可选能力和正常路径。不能根据文件名、同名符号或文档描述猜测实现，也不能把建议、理想行为或间接调用写成现有事实。

### 先定位业务源码，限定读取范围

1. 优先采用用户指定的业务源码路径；已有配置的 repository.path 作为定位线索，须核对是否仍有效。没有明确路径时，先看项目顶层目录和根部构建、启动配置，从入口与项目引用定位自有源码目录。不要把当前工作目录、技能安装目录或整个仓库直接当作业务源码范围。
2. 深入读取前，用简短表格说明本次业务源码目录、相关自有测试与配置，以及排除范围。能够根据已有信息确定时直接继续，不重复请求确认；找不到业务源码或无法区分多个候选项目时，只询问缺失的范围信息，不用技能或工具文件凑出框架。
3. 默认排除下表内容。搜索、列举文件和读取内容时都应用范围限制；先限定业务目录并设置排除项，再执行 rg 等命令。不能先递归扫描或读取整个仓库，再从结果里删掉排除内容，也不能通过隐藏文件搜索、符号链接或调用追踪绕过排除范围。

| 默认排除内容 | 处理规则 |
|---|---|
| 技能与 Agent 配置，如 .agents/、.codex/、.claude/、技能包和 SKILL.md | 不作为业务源码搜索、展开或分析；不把技能流程画成业务模块 |
| 辅助工具、开发脚本、技能自带 tools/ 及模板示例 | 不因位于仓库内就纳入架构，不递归阅读其实现 |
| 第三方依赖，如 node_modules/、vendor/、third_party/、.venv/ 及依赖缓存 | 不进入依赖目录、下载依赖源码或分析库内部实现 |
| 版本管理数据、构建产物、缓存、日志及生成文件 | 排除 .git/、已确认的 build/、dist/ 等产物目录和 docs/archfiy/、docs/archify/ 中的生成网页；已有项目配置可作为维护基准读取 |

依赖清单和构建配置仅按定位业务源码、核实直接依赖所需读取。业务源码调用外部依赖时，追踪到业务侧调用位置为止，只记录可见的名称、调用方式、参数及业务侧处理；不推测依赖内部行为，也不为依赖展开模块、方法和层级。自有多包项目中的业务包可以纳入范围，不能仅因它被另一业务包引用就当成第三方依赖。

执行本技能必需的技能说明、适用的项目协作规则、配置模型及模板说明，只按当前任务需要读取，作为执行规则或工具用法；不得作为业务实现依据，也不扩展阅读其他技能、工具和依赖。使用部署、校验工具不等于把工具本身纳入源码分析。

只有用户明确要求分析某个技能、工具或依赖本身时，才将指定部分纳入目标范围，其余排除规则继续生效。即使仓库内只有技能包或工具，也不自动采用这个例外。

## 2. 执行

### 先核实，再写入

正式配置中每一项都必须核实清楚、实事求是，不允许包含未核实、待确认、猜测或占位内容。

- 空白项目的依据是头脑风暴中已经确定的需求与设计；已有代码的依据是实际定义、调用、默认值、分支、返回结果和副作用。
- 发现疑点，先继续查已确定范围内的业务源码或与用户讨论，不擅自进入排除目录；解决前不生成或替换正式配置，也不部署不完整框架。不能省略疑点涉及的内容，再宣称框架完整。
- 确认不存在或不适用的内容，才使用模型规定的空数组、空字符串或省略可选字段。不能把没查过写成没有，也不能为填满字段编造内容。
- 模型要求保留的 unknowns 统一为 []。这表示内容已核实；不能通过清空 unknowns 掩盖既有疑点。
- 每个方法的输入输出都必须核对完整，正式配置的 inputsConfirmed、outputsConfirmed 均为 true。确认无输入或无输出时，对应数组才可为空。
- planned 表示已确定、尚待实现的设计，不能含糊；verified 表示与实际源码相符，不代表业务测试通过。modified 是语义修改后的过程状态，交付前须重新核对为 verified，或确认其为待实现设计后使用 planned；不能仅改状态代替核实。

### 划分模块和分层

先把本次范围内的职责、真实关系和边界梳理清楚，再划分模块与分层，最后安排位置。模块按职责划分，不机械地把每个文件或函数建成模块；不预设层数、模块数、方法数或连线数。

源码模式下，不能把不存在的服务、消息机制、数据保存操作或依赖加入框架。分组不能隐藏实际执行者、读写归属或影响行为的条件。每个模块和有向关系都要有实际读取过的源码依据。

### 逐项填写模块

先核对项目名称、说明、代码目录和版本，再逐个模块检查下表。纳入本次范围的模块必须完整梳理，不能只抽取几个代表方法，也不能遗漏模板中不直接显示在画布上的内容。

| 内容 | 必须梳理的事项 |
|---|---|
| 基本信息 | 中文名、英文名、功能、语言、代码位置、所属层级 |
| 功能需求 | 具体功能及成立条件；源码模式说明代码实际完成的行为 |
| 依赖项 | dependencies 必填字符串数组，每行一个已确认的模块、库或运行条件；确认没有依赖时为 []，不从画布连线推断 |
| 模块参数 | 名称、类型、用途、默认值和必需标记 |
| 数据结构 | 结构名称，以及每个字段的名称、类型和用途 |
| 方法 interfaces | 名称、用途、全部输入输出、必需标记、默认值、处理流程和错误处理 |
| 消息事件 events | 名称、发送或接收方向、用途、消息参数和处理流程 |
| 测试项 tests | 测试步骤和预期结果；不表示测试已执行通过 |
| 来源与状态 | 实际源码位置、符号、核对状态；需求设计不虚构来源 |

源码模式保留实际 englishName，中文名和说明解释用途，不任意翻译或改名。测试项只记录已有测试的实际含义；需求模式记录确定的测试要求。不生成和运行业务测试代码。

sources 记录实际读过的仓库相对路径、从 1 开始的 line，以及必要的 endLine、symbol。codeLocation 单独保存相对代码目录的路径，多处位置用换行分隔。Git 项目记录实际 revision，dirty 按整个仓库判断；修改过、未跟踪或被忽略的来源文件须说明差异或内容哈希，不能仅用提交号证明当前内容。非 Git 项目不编造提交号。

### 建立关系并自上而下布局

1. 先核对模块之间真实的调用、依赖或消息传递，确定方向与含义，再建立 relations。源码关系须有调用、导入、事件接线或实际读写依据；不能把间接调用画成直接读写。
2. 分层统一从上到下排列，同层模块按主要交互顺序摆放；联系紧密的模块靠近，为箭头与文字留出空间。层级含义来自项目，不硬套固定层数。
3. 按模块实际内容估计节点高度，再安排 x、y 和四边连接点。层级包围框由工具计算，不添加模型没有的宽高或路由字段。
4. 真实存在的反向调用、回调和消息关系保留原方向；不能为外观改关系、删必要内容或编造依赖。
5. 新建框架按此布局；维护已有配置时保留范围外位置。只有用户要求调整布局时才重排已有整体画布。

### 校验并保存配置

| 检查 | 完成标准 |
|---|---|
| 内容正确性 | 每项符合已经确定的设计或实际源码，状态与依据一致 |
| 内容完整性 | 本次范围内的模块、成员、重要条件和必要关系无遗漏；无疑点或占位内容 |
| 源码双向核对 | 从范围内的业务源码查配置是否遗漏；从配置查每项说明是否有依据 |
| 分析边界 | 架构模块和 sources 均属于本次明确的分析范围，没有混入排除的技能、工具、依赖实现或生成文件 |
| 数据结构 | Model.validate 无 errors；warnings 逐项处理，不填假数据消除提示 |
| 修改范围 | 稳定 ID、用户编辑、范围外字段和关系得到保留 |

使用 globalThis.EasyCode.Model；Node 或网页中均可调用模型校验。新项目用 createProject，模块和成员用对应 createModule、createInterface、createParameter、createStructure、createStructureField、createEvent、createTest 创建，再填入真实内容。不能保留创建函数的默认示例文字。

更新已有语义使用 Model.updateModule、updateInterface、updateMember、updateRelation 等函数。对象 ID 全局唯一，改名不换 ID；删除时清理失效引用。方法 flow、errors 和事件 flow 是逐行字符串，参数 defaultValue 保存字符串，不能改变字段类型。

正式配置为 archify.json，内容是带两空格缩进和末尾换行的纯 JSON 对象，不含脚本赋值、注释、函数或 __proto__ 字段；保留已有字段、稳定 ID 和布局。完整字段指导书 archifytemplate.template.jsonc 仅用于说明，不是正式数据。

[project-file.js](../../tools/html/assets/project-file.js) 的 EasyCode.ProjectFile.parse / stringify 统一负责 JSON 解析和生成，不执行文件。Agent 读取并记录原内容或哈希，写入前再次检查，变化时处理冲突；写入后解析、校验并深度比较。可用 [files.mjs](../../tools/html/scripts/files.mjs) 的 readProjectFile / writeProjectFile 和 expectedVersion 完成检查。不能用工具空框架覆盖项目现有数据。

### 围绕配置部署网页

框架配置完成并通过上述检查后，继续部署网页供用户阅读和修改；用户明确只要配置时按其范围交付。只修改已有配置时不重新部署程序，也不重新生成入口。

默认使用 Node.js 22+ 生成并启动 HTTP 网页服务，不再默认复制本地文件后双击打开：

1. 检查目标项目 docs/archfiy/ 或用户指定目录，沿用当前已保存的 archify.json；保留用户内容和网页定制。已有不同数据时先确定当前基准，不用空框架覆盖。
2. 从 xyf-easycode 根目录运行 `node tools/html/scripts/deploy.mjs "<目标项目根目录>" --output-dir docs/archfiy --source-file "<已核实的archify.json路径>"`。目标已有相同配置时保留；仅更新配置不用重新生成网页。输出应位于授权项目范围内，不能与技能工具源目录重叠。
3. 命令生成 index.html、部署 html/ 并启动服务。默认在 10000～65535 中随机选择空闲端口，占用时重新随机选择。启动并检查成功后交付实际 HTTP 地址。Node 缺失或服务无法启动时说明阻碍，不把文件路径当作已可访问的网页。
4. 服务启动成功后自动生成或更新部署目录的 ReadMe.md，记录实际地址、端口、archify.json 和 `node html/server.mjs` 重启命令。重启后地址可能改变，以更新后的说明为准。保留 ReadMe.md 中生成区域外的用户备注。

网页打开时通过服务自动读取 archify.json；点击“保存配置”或 Ctrl+S 直接写回同一文件，无需原生文件选择器。服务按文件版本检查冲突，写入后读回核对。约每 2 秒检查外部更新；无未保存编辑时刷新内容，有未保存编辑或编辑窗口打开时保留编辑并提示。刷新、重新打开或重启后仍读取同一 JSON。

“另存为配置”下载 JSON 副本，不改变服务绑定的数据文件；“HTML 快照”供分享，不表示配置已保存。导入 JSON 后需点击保存才写入服务配置。读取、导入或保存失败时保留当前编辑。

服务默认只监听本机。部署命令保持运行以提供网页，可按 Ctrl+C 停止；已有同目录服务时核对并复用实际地址。用户指定五位数端口可传 `--port`；`--no-start` 只生成文件，不能报告服务已启动。仅明确要求手动文件模式时使用 `--mode local`，需要手动选择 JSON，不自动读取同目录配置。

修改网页源码或运行模板后，使用 `node tools/html/scripts/build.mjs --runtime` 更新工具入口；默认生成服务版。独立快照使用 `build.mjs <archify.json路径> <HTML输出路径>`，不能覆盖编辑器入口。

### 已有配置的指定修改与数据取回

按稳定 ID、所属模块和对象种类定位修改范围；不能因为中文同名而批量修改无关对象。新语义同样必须核实清楚，保留范围外字段、来源与布局。读取已有内容发现疑点时先解决，不清空标记冒充已核实，也不擅自扩大修改范围。

名称翻译仅更新指定 englishName 及相应状态。结合已确定的用途、类型和项目命名习惯处理，检查标识合法性和重名；已有源码标识按代码保留。用户明确要改变已有代码名称时，将确认的新名称作为 planned 设计，不把它标成现有源码事实，也不在本技能中改业务代码。可以使用 [translation.js](../../tools/html/assets/translation.js) 的 formatName 整理格式，该函数不负责语义翻译。

服务入口没有 ec-project 快照，取回数据时解析实际使用的 archify.json；若已是当前文件则不重复写入。另存为副本不改变服务的数据基准。明确指定独立 HTML 时，使用 [serialization.js](../../tools/html/assets/serialization.js) 的 EasyCode.Serialization.readProject 解析数据块，不执行页面脚本、不从外观猜测内容。提取结果先检查完整性与事实依据，发现疑点先处理；通过后保留字段和 ID，检查目标版本再保存并读回比较，不拿旧快照自动覆盖当前设计。

## 3. 检查与交付

数据修改均做内容核实、模型校验、范围差异检查和保存后读回比较。运行 `node tools/html/scripts/check.mjs "<部署目录>/index.html"` 检查配置与网页，再运行 `node tools/html/scripts/check.mjs --url <实际HTTP地址>` 核对服务、磁盘 JSON 和 ReadMe.md 地址一致。

保存、服务重启、外部更新、未保存冲突、导入和损坏 JSON 的验证使用独立临时项目，不向正式框架加入测试数据。检查随机端口为五位数，ReadMe.md 记录的是成功启动后的地址；重启后同步更新。检查失败先处理，不能用旧产物当新结果。
