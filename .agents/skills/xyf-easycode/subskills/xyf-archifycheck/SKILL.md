# XYF ArchifyCheck

以用户确定的文档为依据，逐项核对真实代码，报告符合、不符合和无法确认的内容。在当前 Agent 中完成检查，默认不修改代码、架构或文档。

## 1. 确定依据和范围

沿用用户已指定的目标项目、文档、模块和已有授权；未限定模块时检查文档覆盖的全部模块。文档优先使用用户指定的文件；没有指定时，使用目标项目的 `docs/archfiy/archify.json`。旧项目实际使用 `docs/archify/archify.json` 时沿用；两处都有数据且基准不清时，只询问缺少的基准信息。不能用技能工具自带的空框架、示例或旧快照代替项目需求。

读取项目协作规则，确定文档实际路径和代码根目录。架构的 `repository.path`、`codeLocation` 仅作为定位线索，核实文件和实际入口后继续追踪。用户未指定源码范围时，从项目构建、启动配置定位自有源码；默认排除技能目录、第三方依赖、缓存和生成网页，用户明确要求检查这些对象时才按指定范围读取。

记录本次文档的版本或内容哈希，以及源码版本和相关未提交改动。检查的是当前文件，不能仅凭提交号或文档中的 `sources` 声称已核对源码。相关文件在检查中变化时，重新核对受影响项。

架构 JSON 使用 [project-file.js](../../tools/html/assets/project-file.js) 的 `EasyCode.ProjectFile.parse` 读取，用 [model.js](../../tools/html/assets/model.js) 的 `EasyCode.Model.validate` 检查结构；字段说明见 [完整模板](../../tools/html/templates/archifytemplate.template.jsonc)。不运行补默认值、改状态或回写配置的函数。其他需求和接口文档按实际标题、条款或接口定位，不要求转换为架构 JSON。

文档为空、缺失、互相冲突或关键含义不清时，将相关项标为“无法确认”，继续检查不受影响的部分；只有影响本次判断的关键信息才向用户询问。不自行补充需求或替用户确定新方案。

## 2. 逐项核对实现

先列出本次范围内的模块、公开成员和需求，再从入口、注册和调用位置追踪到实际执行、数据读写与返回位置。名称相同、注释相符、方法存在或界面上有按钮，都不能单独证明功能符合文档。逐项记录证据，检查数量较多时分批完成，不抽查后声称全部符合。

| 文档内容 | 检查要点 |
|---|---|
| 模块功能、具体需求 | 正常路径、重要条件、执行结果和必要副作用是否实现，有无缺失、空实现或固定返回值 |
| 分层、语言、代码位置 | 文档明确规定的模块归属、代码路径和语言是否符合；缺少约定时不自行套用目录规则 |
| `dependencies` | 每项明确的依赖是否在真实调用、导入、注册或运行条件中得到满足；空白项标为无法确认 |
| 参数、数据结构、方法输入输出 | 公开英文名、字段、类型、必需标记、默认值和返回行为是否符合约定 |
| 方法用途、`flow`、`errors` | 具体步骤、顺序、分支和错误处理是否由实际代码完成，不能只查注释 |
| 消息事件 | 发送或接收方向、事件名、消息参数、处理流程和接线是否一致 |
| 测试项 | 已有测试是否覆盖规定的步骤和预期；静态阅读、运行结果和未执行的测试分别说明 |

方法仍存放在 `interfaces` 中。`inputsConfirmed` 或 `outputsConfirmed` 为 false 时，不能把空列表解释为已确认没有输入或输出。`defaultValue` 缺失或为空表示文档未设默认值，不能擅自推导为 `0`、`false` 或空字符串；只有文档明确约定时才判断默认值是否符合。架构状态 `verified` 不代表业务测试通过。

`relations` 是画布标注，不用箭头决定代码依赖；依赖判断使用 `dependencies` 中的明确要求和实际源码。实现中额外的内部辅助函数或文档没有约束的行为，不自动判为不符合；只有它影响、遗漏或违背文档约定时才列为问题。

发现不一致时，给出文档位置、代码位置、具体差异和影响；声称“未实现”前，检查本次源码范围内的注册、调用和替代执行路径。资料不足或依赖行为无法从现有代码确认时，说明缺少什么证据，不把推测写成代码缺陷。

## 3. 操作边界与验证

默认只做静态检查，不安装依赖、构建、运行测试、启动服务或写入报告文件。当前任务明确授权运行验证时，按项目规则复用已有测试，记录实际命令、结果及覆盖范围；沿用已有授权，不重复请求。不能把存在测试文件、历史通过记录、模拟结果或未执行的检查写成本次通过。

不修改实现来消除检查问题，也不修改文档来迎合代码。用户要求修复时，带上已确认的问题和范围交给 [xyf-code](../xyf-code/SKILL.md)；用户要求调整架构时使用 [xyf-archify](../xyf-archify/SKILL.md)，不因发现差异就自动进入修改流程。

## 4. 输出结果

先报告检查范围和主要问题，再按需给出逐项核对表：

| 模块或需求 | 文档依据 | 代码证据 | 结果 | 差异与建议 |
|---|---|---|---|---|

文档和源码均给出可定位的文件路径及行号；架构项附模块或成员的稳定 ID。结果只使用“符合”“不符合”“无法确认”，说明是静态核对还是有本次运行验证支持。

有明确不一致时，整体结论为“不符合”；没有明确不一致但仍有无法确认或未覆盖项时，为“无法确认”；仅在本次范围全部核对且有充分证据时，才给出“符合”。静态核对符合不等于运行验收通过。未检查的模块、未运行的测试和环境阻碍单独列明，不能计入已通过范围。
