# XYF Code

主代理负责计划、调度、文档核对、整体代码审查和交付；开发子代理负责实现、测试及修复，独立审查子代理负责模块代码审查。完整开发按下面六步执行，第 2～4 步可按依赖分批推进。检查通过前，不能把模块记为完成。

严格按已确认的架构实现，不自行删减、替换、简化或改变方案。沿用本次已有的有效确认；明确限定的单项任务按用户范围执行，不能把只读检查自动扩展为开发。

## 1. 检查差异，制定计划

负责人：主代理。通过条件：差异及依赖有证据，开发计划明确，已取得所需确认。

- **确认真实依据。** 读取目标项目协作规则、源码和构建配置。架构优先使用用户指定或 xyf-archify 交付的路径，默认 `docs/archfiy/archify.json`；旧项目使用 `docs/archify/archify.json` 时沿用。两处都有数据且基准不明时先解决，不能拿工具的空框架当业务需求。编码前报告并确认实际配置绝对路径及全部模块或指定模块、方法的范围；已有明确确认不重复询问。
- **主代理先检查。** 在当前主代理中使用 [xyf-archifycheck](../xyf-archifycheck/SKILL.md)，逐项记录符合、不符合和无法确认的内容。按其规则解析架构、校验数据，处理结构错误及本次相关警告；不修改代码、补默认值或回写文档。以当前已保存架构为需求、真实源码为已有实现依据；记录文档内容哈希、开发前源码状态（含已有未提交改动）及本次审查基准，保留用户原有改动。
- **不能猜关键设计。** 架构为空、需求冲突、公开名称无效、输入输出未确认或重要信息缺失时，暂停受影响任务，说明缺项并询问。用户确认可作为本次依据，但不因此自动回写架构。不受影响的任务可继续；既有代码符合的部分不为凑任务而重写。
- **依赖必须有依据。** 按模块稳定 ID，结合明确的 `dependencies`、公开接口和实际调用安排顺序；`relations` 只是画布标注。依赖不明、循环或接口冲突时，先解决调度与前置条件，不能把相互依赖的任务标为独立任务。未完成的前置模块须通过第 3、4 步，已有依赖须有本次核对的可用依据，才能放行依赖它的开发任务。
- **计划必须可分配、可验收。** 用表格列出模块 ID、差异及证据、依赖与先后顺序、开发任务、负责人、允许修改的文件和验收要求，标明并行组、共享文件及阻碍。批量写入前按项目规则确认计划及文件范围，沿用仍适用的已有授权；不得靠分给子代理绕过确认。

实现时按以下字段理解架构，字段细节见 [完整模板](../../tools/html/templates/archifytemplate.template.jsonc)：

| 架构内容 | 实现依据 |
|---|---|
| groups、groupId、englishName | 所属层级；代码根目录下使用层级英文名作为目录，不强制语言命名空间 |
| repository、language、codeLocation | 代码根目录、语言、相对代码位置；缺少路径时沿用现有结构，不擅自迁移代码 |
| purpose、requirements、dependencies | 模块功能、需求与明确的依赖；依赖项是文字，不擅自推断含义 |
| parameters、structures、interfaces、events | 公开参数、数据结构、方法、事件及其类型、默认值、输入输出、流程和错误处理 |
| tests | 必须验证的步骤与预期，配置中存在测试项不代表已通过 |

方法仍存放在 `interfaces` 中。`defaultValue` 缺失或为空表示文档未设默认值，不自行当作 `0`、`false` 或空字符串；输入输出未确认时，不把空列表当作已确认没有输入输出。分层或公开名称缺失、无效、冲突，或既有结构与要求冲突时先确认，不自行命名公开接口。

## 2. 多子代理并行开发

负责人：主代理调度，开发子代理实现。移交条件：模块实现及必要测试完成且通过，开发负责人已停止写入。

- **任务信息必须完整。** 每个子代理收到项目和架构实际路径、模块 ID、需求与差异、依赖现状、文件范围、测试目录绝对路径及可写子目录、验收要求、已有授权、文档版本和审查基准。一个开发子代理一次只负责一个模块，不顺带改其他模块。
- **依据变化必须同步。** 架构或关键依赖变化时，主代理立即暂停受影响任务，核对新依据、更新计划并交接上下文；受影响的旧通过结论失效，不能让子代理继续按旧版本开发。不猜测历史变更，必要时对照可信旧配置和实际调用方。
- **禁止交叉写入。** 独立且前置条件满足的模块并行开发；同一时间一个模块只有一个开发负责人，同一文件只有一个写入者。共享文件由主代理处理或安排串行修改。更换负责人或交给审查前，必须确认原负责人已停止写入并完成交接，不能覆盖用户或其他代理的改动。
- **实现不能偏离方案。** 公开名称、类型、明确约定的默认值及行为必须符合架构；内部辅助代码可自行组织。方法、事件有 `flow` 时逐步实现，每步前添加目标语言有效的编号注释；无 `flow` 时自行安排步骤，仍添加编号注释并满足需求。复用现有库和惯例，不为事件另建消息服务，不用空实现、固定返回值或伪造结果冒充完成。
- **测试目录必须固定。** 本步骤的单元、模块测试及第 3、4 步返工测试，必须在目标项目根目录下的 `docs/archify/test/` 及其子目录内编写和运行。测试入口、用例、夹具、临时数据、缓存、日志、覆盖率和报告均放在其中；测试工作目录、工具临时目录和产物输出目录也须设在其中。目录不存在时在已有写入授权内创建，按模块或任务划分子目录，避免并行测试相互覆盖。
- **复用测试不能绕过目录要求。** 可引用目录外的业务源码并复用现有测试工具，不擅自迁移或删除已有测试；本次使用的测试入口、用例及产物仍须位于上述目录。工具不支持时先在授权范围内适配，仍无法满足则报告阻碍，不能绕过要求运行测试。
- **必须验证实际行为。** 按上述目录约束复用项目测试能力，覆盖架构 `tests` 的步骤和预期；没有测试项时也要按需求验证实际功能，并运行必要的构建、类型检查。为测试执行的构建、类型检查同样遵守上述工作目录和产物约束。报告实际工作目录、命令、结果及未覆盖内容，不把测试文件存在或历史通过当作本次通过。
- **完成报告不能代替验收。** 子代理报告模块 ID、改动文件、审查范围、测试结果和阻碍后停止写入，等待主代理核对；不假设存在自动 Hook，不自行宣告模块验收通过。多代理不可用或被上级规则禁止时说明阻碍，不冒充并行开发已执行。

## 3. 主代理核对模块文档与代码

负责人：主代理。通过条件：该模块范围内逐项核对为符合，且没有未解决的无法确认项。

- **由主代理亲自核对。** 在当前主代理中使用 [xyf-archifycheck](../xyf-archifycheck/SKILL.md)，读取该模块文档与真实执行路径，覆盖需求、依赖、公开成员、输入输出、流程、错误处理和测试要求，不能用子代理自评或名字相同代替检查。
- **只读并记录证据。** 核对时不改代码或文档；记录模块 ID、文档与源码内容版本、覆盖范围、结论及文件行号。被检查文件和影响结论的依赖不得并发修改；发生变化后重新核对受影响项。
- **未通过必须返工。** 不符合时将具体差异交回开发负责人，按第 2 步约束修复并测试后，重做受影响的文档核对；无法确认时补齐证据或说明阻碍，不能记为符合。静态核对符合不能代替运行测试。
- **通过后才能进入第 4 步。** 通过只在主代理的任务记录中登记，不回写架构状态；不能因为测试通过就跳过文档核对。

## 4. 独立子代理审查模块代码

负责人：独立审查子代理，主代理安排与跟进。通过条件：完成指定改动的审查，发现的缺陷已修复并复查。

- **必须独立审查。** 主代理明确要求审查子代理使用 [review-agent](../review-agent/SKILL.md)，不能由该模块本轮开发或修复者自审。传入项目规则、模块范围、审查基准及相关未提交改动，确保实际审查的是本轮最终代码。
- **遵守只读边界。** 审查子代理不修改文件、不提交、不推送，也不再转交其他代理审查。读取完整目标差异、必要的上下文、调用方和测试；按该技能报告有证据的新引入缺陷、P0～P3 严重程度和准确位置，不编造问题或夹带无关风格调整。
- **返工后重查。** 缺陷交回开发负责人，按第 2 步约束修复并测试；主代理重做受影响的第 3 步，再交独立审查子代理复查。每条问题都必须有处理结果和复查证据，不能把“已回复”当作“已修复”。
- **无发现不等于测试通过。** 保留审查范围、源码内容版本、结论及测试缺口；仅在第 3、4 步和模块测试均满足要求后，将该模块记为完成。修改影响已通过的依赖模块或调用方时，必须重新检查它们。

## 5. 主代理整体审查，子代理并行修复

负责人：主代理亲自整体审查，开发子代理按计划修复。通过条件：集成验证通过，整体审查发现的问题完成修复与复查。

- **先确认模块全部完成。** 检查本次计划中的模块均通过第 3、4 步及模块测试，所有开发者已停止写入，再核对最终集成状态。不能把模块分别通过当成整体集成通过。
- **主代理必须亲自整体审查。** 按 [review-agent](../review-agent/SKILL.md) 的规则，检查本次范围相对既定基准的全部最终改动及相关调用路径，重点检查跨模块接口、真实依赖、数据传递、错误传播和兼容性。不能仅汇总子代理报告，不能只检查最后一次修复的差异。
- **集成与回归测试目录必须固定。** 整体验证和修复后的回归测试，必须在目标项目根目录下的 `docs/archify/test/` 及其子目录内编写、运行并保存产物。工作目录、测试文件、临时数据、缓存、日志和报告遵守第 2 步的测试约束，独立并行任务使用不同子目录。
- **必须做集成验证。** 按上述目录约束复用项目已有集成测试能力和运行方式，覆盖本次变化涉及的跨模块行为，并执行必要的构建、类型检查。报告实际工作目录、命令及结果；环境或依赖阻碍验证时，说明影响，不能宣称整体验收通过。
- **修复计划必须明确。** 主代理将缺陷证据、严重程度、影响模块、修复任务、负责人、文件范围、依赖和复查要求列成表格。独立修复并行，共享文件和有依赖的修复串行，继续遵守第 2 步的单写入者规则；超出原授权范围先确认。
- **修复后必须闭环。** 修复先完成相关测试，再重做受影响的第 3、4 步；主代理复查缺陷和受影响的跨模块行为，并确认原整体审查的其余结论仍适用于最终代码。反复无进展时说明原因并暂停受阻任务，不无限重试或跳过问题交付。

## 6. 最终验收与交付

负责人：主代理。通过条件：本次范围内的实现、测试、文档核对和代码缺陷处理全部完成。

- **核实最终版本。** 确认没有代理继续写入，核对最终文档、源码内容（含未提交改动）和覆盖范围。只有输入内容、范围及审查基准仍一致时，才复用已有检查结果；变化后重查受影响项。最终文档核对须覆盖全部指定模块及受改动影响的模块关系，不能用部分模块结果声称全部符合。
- **验收测试必须遵守目录约束。** 最终验收或补测须在目标项目根目录下的 `docs/archify/test/` 及其子目录内完成，执行和产物要求沿用第 2 步。主代理核实各阶段测试的实际工作目录、日志及报告位置，并在交付时给出该目录内的测试证据路径。
- **不能带着未知项宣告完成。** 必需测试未运行、测试失败、文档无法确认或审查缺陷未处理时，只报告实际进度和阻碍；不得将静态符合、`No findings.` 或架构 `verified` 当作运行验收通过。用户明确缩小交付范围时，记录排除项及影响，不能暗中删减计划。
- **默认禁止回写架构。** 不因实现完成而改 `archify.json` 的代码位置、来源、状态或版本，主代理与子代理均须遵守。当前方案无法实现时，立即暂停受影响工作，说明原因、影响和建议；只有用户明确确认新方案及回写范围，才由总入口交 [xyf-archify](../xyf-archify/SKILL.md) 处理，保留其他内容及稳定 ID，再更新计划并重做受影响检查。不能改文档来掩盖代码偏差。
- **交付必须可核查。** 用简短表格列出完成模块、实际改动文件、模块与整体测试、文档核对及代码审查结论，说明未覆盖项和遗留限制。写入只能发生在目标项目授权范围，不写入技能工具或其他项目；提交、推送、合并和发布只按用户明确要求执行。
