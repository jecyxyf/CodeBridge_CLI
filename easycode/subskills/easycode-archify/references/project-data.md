# Project data, format 1

`assets/model.js` is the schema authority. `Model.validate(project)` returns `{errors:[{path,message}],warnings:[{path,message}]}` without throwing on malformed data. Fix errors before building/saving; empty draft names, purposes and parameter descriptions produce warnings.

| Object | Fields |
| --- | --- |
| project | `formatVersion:1`, `id`, `name`, optional `englishName:string`, `description`, `repository`, `groups:[]`, `modules:[]`, `relations:[]`, `view` |
| repository | `path:string` (selected directory name or manually entered path), `revision:string` (code version/reference displayed in the title), `dirty:boolean`; version identifies the described code, not the HTML editor version |
| group | `id`, `name`, optional `englishName:string`, `color` (title text, use `#rrggbb`), optional `backgroundColor` (`#rrggbb`), `x:number`, `y:number` |
| module | `id`, `name`, `purpose`, `groupId` (existing group ID or `''`), `x`, `y`, `status`, `sources:[]`, `unknowns:string[]`, `interfaces:[]`; optional `englishName:string`, `language:string`, `codeLocation:string`, `requirements:string[]`, `parameters:[]`, `events:[]`, `tests:[]` |
| interface (method) | `id`, `name` (legacy signature allowed), `purpose`, `status`, `sources:[]`, `unknowns:string[]`, `inputsConfirmed:boolean`, `outputsConfirmed:boolean`, `inputs:[]`, `outputs:[]`; optional `englishName:string`, `flow:string`, `errors:string` |
| parameter | `id`, `name`, `type:string`, `description`; optional `englishName:string`, `defaultValue:string`; inputs require `required:boolean`; other parameters may omit `required` (if supplied, boolean) |
| event | `id`, `name`, `englishName?:string`, `description`, `direction:emit/receive`, `trigger:string`, `parameters:[]` (payload) |
| test item | `id`, `name`, optional `englishName:string`, `steps:string`, `expected:string` |
| relation | `id`, `from:moduleId`, `to:moduleId`, optional `fromPort` / `toPort` (`top/right/bottom/left`), optional `label:string`, `status`, `sources:[]`, `unknowns:string[]`; legacy optional `type:call/dependency` is preserved but not shown |
| source | `{path:string, line?:positiveInteger, endLine?:positiveInteger, symbol?:string}`; nonempty path; endLine requires line and cannot be smaller |
| view | finite `x`, `y`, positive `scale`, `expanded:moduleId[]`, `expandedInterfaces:interfaceId[]` |

All IDs are globally unique strings, starting with a letter and containing only letters, digits, `_` and `-`. Creation helpers generate them; retain existing IDs on updates. Coordinates must be finite. The UI constrains zoom to 25%–180%. A relation needs two different existing modules; identical `(from,to,type,label)` entries are rejected. Expanded IDs must exist and cannot repeat.

Canvas cards are read-only summaries: name, a short responsibility preview, member counts and evidence status. The edit icon opens a scrollable module dialog with all fields. Dialog edits use a separate draft; Confirm validates and applies it, Cancel/Escape discards it. New modules are added only on Confirm. Delete is available in the existing module's dialog, with confirmation that also names the number of affected relationships. Confirm/Cancel/Delete share the same neutral icon-button style and remain visible at the bottom. HTML Save happens after dialog confirmation; Ctrl+S in the module dialog asks the user to confirm or cancel first.

The dialog header shows Chinese / English module names on the left and language on the right. It follows edits and translated names immediately; a single name has no slash, both blank show 未命名模块, and blank language shows 未设置语言. Long names wrap to at most two lines; language truncates, with full text available on hover. The dialog has six collapsible groups. Module information starts open, showing bilingual name, programming language, responsibility, code location and layer. Language offers common suggestions and permits custom input. Functional requirements sit directly below module information and also start open. Parameters, Methods, Message events and Test items start closed with counts, without an extra external-interface heading. Each member can collapse independently; method inputs, results, implementation flow and event payloads also have their own fold controls. Adding a member opens its group and the new row, then focuses its first field; deleting one retains siblings' fields and expansion. Fold controls use real buttons with `aria-expanded` and `aria-controls`; collapse changes only the DOM, keeping the draft intact.

`requirements` is an ordered array of strings, defaulting to an empty array for new modules. Each text row holds one requirement, including any line breaks; blank draft rows are allowed. The add button (新增需求) opens the section and focuses the new row. A row's delete icon removes only that row, retains siblings and moves focus to the next row, previous row or add button. The count and empty message follow the current draft. Input labels and delete labels reflect the current row positions. Text edits do not rebuild rows, preserving input focus and composition. Changes use `updateModule`, so editing checked requirements marks the module as modified; Confirm validates the list before applying it, and Cancel/Escape discards all changes.

Names use one row and two columns, Chinese on the left (`name`) and English on the right (`englishName`), for projects, groups, modules, parameters, methods, events and tests. English fields are optional for old format-1 data; opening, refreshing or unchanged confirmation must not backfill them. Model validation permits either name first and warns only when neither is filled. Project/layer forms require a Chinese name. Keep existing single names unchanged rather than guessing a translation. `Model.displayName` prefers Chinese/legacy name, then English, for configuration and feedback labels. Canvas module labels and tooltips show only `name` or a Chinese unnamed placeholder. Parameters describe public configuration/attributes, with type, description and optional default; method-specific parameters belong under that method. Methods also have purpose, optional implementation flow and errors. Events specify emitted/received direction, trigger and payload. Tests record steps and expected result.

The English-input translate icon is explicit opt-in per click: `Translation.createClient` calls MyMemory `https://api.mymemory.translated.net/get` with only `q` and `langpair=zh-CN|en`, no credentials or referrer. Anonymous service is currently limited to 5,000 characters/day and 500 UTF-8 bytes/request. It requires internet and does not promise stable service or accurate code terminology. `formatName` converts a valid English response into project kebab-case, module/group PascalCase, or member camelCase; it does not change meaning, infer tense/boolean prefixes, or generate random synonyms. No Agent, backend or runtime package is required.

The optional network request has a 12-second timeout; successful phrases are held only in a bounded page-session cache. Errors, quota exhaustion and Chinese/invalid results preserve the current input. `Translation.attach` writes only to the current dialog field and dispatches its normal edit event; user typing, removal, cancellation and dialog closure invalidate stale results. Confirm applies the draft, and Save persists it using the existing path. Translation caches and transient request state are never project data.

`interfaces` remains the stored method list. New constructors include empty defaults; do not backfill data on open. `codeLocation` contains one file or directory per line, relative to the project's code directory. `Model.normalizeCodeLocation` trims lines, removes blank lines, normalizes Windows separators and ./ prefixes, and resolves internal dot segments. Confirm applies that normalization on a copy before validation; absolute paths, drive letters, line-number suffixes and paths escaping the project directory are rejected. Blank locations stay blank; existing source paths are not substituted. No filesystem lookup or old-path migration is performed. Source evidence stays separate and preserved inside collapsed details; a code location alone does not establish verified evidence. `language` is a freely editable string, not a fixed enumeration.

Each module has one connection point at the middle of each edge. Hold a point, drag to a point on another module, and release to create a relation. The drag starts at the output and ends at the input; points have no fixed role and may serve multiple relations. Single clicks do not connect. Dragging shows a highlighted preview following the pointer. Escape, pointer cancellation, or releasing on blank canvas/the same module cancels without modifying data. Connections start directly from these points; there is no toolbar or footer connection button. New arrows have no `type`, and all arrows share one style. They only help readers understand module relationships. Duplicate detection still uses `(from,to,type,label)` regardless of side, treating absent type/label as empty strings.

There is no arrow configuration dialog. Left-click a saved arrow or its text to select it. Its line and arrowhead turn bright orange (`#ff9f43`), with no selection rectangle. Two icon buttons, Edit and Delete, appear below the actual curve midpoint, outside the scaled world so their sizes stay readable. They follow pan, zoom and module movement, stay within the viewport and clear the annotation text. Click Edit to open an isolated inline text draft; double-clicking does not open it. Enter or blur applies it, Shift+Enter adds a line, and Escape discards it; IME composition does not submit. The buttons hide while the draft is open and return when it closes. Text may be empty without a warning or placeholder label. Click Delete, or press Delete/Backspace on the selected arrow, to remove it with confirmation; those keys inside a text field only edit text. Click blank canvas or press Escape outside the text editor to deselect and hide the buttons. Keyboard users can focus an arrow and press Enter/Space to select it and focus Edit. Selection and button visibility are transient UI state and do not dirty the project. Save finishes the active annotation before taking its snapshot, and unsaved annotation drafts participate in the close-page warning.

New arrows save `fromPort` and `toPort`. Format-1 files without these optional fields remain valid and choose left/right sides from relative module positions; do not migrate or overwrite their project data just to refresh the editor. Preserve legacy type/evidence fields even though the arrow UI does not expose them. Explicitly chosen sides remain fixed when a module moves. Preview state is not stored. `Canvas.createConnection` owns drag state through `begin` / `complete` / `cancel` and calls `onChange` only after a valid completed relation; `Canvas.relationGeometry` computes curves from current module bounds and saved sides.

Keep the format-1 `view.expanded` and `view.expandedInterfaces` fields for compatibility. Cards no longer expand. Dialog sections use the defaults above instead of the legacy expansion list; toggles are local to that dialog and do not dirty the project. Deleting modules/methods still removes obsolete expansion references.

Group borders are transparent. `color` controls the group title text; titles use 20px semibold type, defaulting to white (`#ffffff`). Background color defaults to `#81b3e9` (RGB 129, 179, 233), independently of the title color, with fixed 50% transparency. Existing groups without `backgroundColor` use that default blue. New groups should include both defaults. Only the background fill is translucent; titles and module content keep their normal opacity. Preserve explicitly chosen colors when updating or saving a project; do not add an adjustable opacity field.

Action buttons use the local SVG icons in `assets/icons.js`, with descriptive `aria-label` and hover `title` text. Project and interface names remain readable content beside their icon buttons. Keep icons embedded in the generated HTML; do not introduce external fonts or assets. Network access occurs only after an explicit click on the English-name translation icon.

## Meaning of evidence and unknowns

- `planned`: a proposal, not a checked implementation.
- `verified`: checked against the stated source version. Modules, interfaces, and relationships each require at least one valid source. Validation checks the shape, not whether that code actually supports the claim.
- `modified`: a previously checked fact was edited and needs rechecking. `markEdited(item)` changes only `verified` to `modified`.

An empty parameter list plus `inputsConfirmed:false` / `outputsConfirmed:false` means unknown, not zero parameters. Set confirmation true only when absence or the listed signature was established. Write unresolved points in `unknowns`; do not invent types, outputs, dependencies, or business rules to fill space.

## Public editing helpers

```js
import '../assets/model.js'; // adjust relative to the calling script
const M = globalThis.EasyCode.Model;
const project = M.createProject('Project');
const module = M.createModule({name:'Module',purpose:'Responsibility',x:100,y:100,groupId:''});
project.modules.push(module);
const api = M.createInterface(); // name/purpose empty, both confirmations false
const parameter = M.createParameter(); // type '未知', required false
M.updateModule(project,module.id,{purpose:'Updated responsibility'});
// Attach api/parameters using updateModule / updateInterface when editing existing facts.
```

`createModule(options)` accepts only name, purpose, groupId, x, y; status and evidence start as planned/empty. `createInterface()`, `createParameter()`, `createEvent()` and `createTest()` accept no options. There is no createGroup helper: construct the group shape with a fresh valid ID.

`updateModule(project,id,patch)` and `updateInterface(project,moduleId,interfaceId,patch)` update supported fields. Interface semantic changes also mark the module; module position/group changes do not invalidate evidence. `removeModule` removes its relationships and expansion records; `removeGroup` ungroups its modules; `addRelation(project,options)` validates endpoints and duplication. `validate` is still required after edits.

`updateMember(project,moduleId,collection,itemId,patch)` edits supported fields of a module parameter, event or test (`collection` is `parameters`, `events` or `tests`) and marks the owning module when changed. Module collection arrays can be added/removed through `updateModule`. For nested method parameters use `updateInterface`; for event payloads use `updateMember` with the event's `parameters` patch. IDs across all collections, including payloads and test items, share the global uniqueness rule. New collections and their nested fields are validated before commit/save; empty drafts can warn without preventing a save.

`updateRelation(project,id,patch)` validates before applying changes to `from`, `to`, `type`, `label`, `fromPort`, and `toPort`. It returns false for an unchanged relation. Side-only edits preserve evidence status; changes to direction/type/description mark verified relations as modified. Setting a port to `undefined` removes that optional field and restores automatic side selection.

`removeRelation(project,id)` removes only that arrow and returns whether it existed. `Annotations.begin` creates an isolated text draft; `Annotations.commit` applies only changed text and rejects stale/deleted arrows. `Annotations.create` owns the inline editor, keyboard controls, positioning and draft checks.

`ModuleEditor.begin(project,moduleId?,position?)` returns an isolated session with `project` (draft), `module`, and the original snapshot. Apply the Model helpers to that draft. `ModuleEditor.commit(project,session)` validates before updating the live module, preserves unrelated current data, rejects a stale session, and returns false for an unchanged existing module. `hasChanges(session)` checks draft changes for the close-page warning. `ModuleEditor.create({session,confirm,onSummaryChange})` builds the form and reports module edits for the live header; `Dialogs.editModule` owns Confirm/Cancel/Delete and dirty-state notifications.

## Header and footer

The title area is a native button that opens project settings. It fills the remaining header width beside the actions; the title and description have the same available width, truncate with ellipses and expose their full text in `title` attributes. Both lines remain visible on narrow screens, with actions on a second row. Project settings expose bilingual name, description, code directory and version. There is no working-mode UI or project `mode` field, default, validator, or compatibility migration. Form edits stay in a draft until Confirm; Cancel/Escape discards them, unchanged confirmation stays clean, and pending edits participate in the close-page check. Save/import asks the user to finish or cancel an open project-settings dialog.

The code-directory field has a folder button. Its synchronous click starts `showDirectoryPicker` with read-only access and a stable picker ID. Only `handle.name` is copied into the draft; no files are enumerated or read, and the handle is not persisted. Browser APIs do not expose the absolute path, so the UI explains that full paths remain manually editable. Cancellation leaves the path intact; failures and unsupported browsers allow manual entry. A pending picker cannot overwrite later typing or a reopened dialog.

`Model.projectTitle` supplies the heading, hover title, browser tab, and serialized HTML title from separate `name` and `repository.revision` fields. Numeric versions gain one `v`, an existing leading `v` is retained, and empty versions add nothing (`软件框架图v0.0.1`). Git hashes and other non-version references are displayed after a space without adding `v`. Formatting trims display whitespace but does not rewrite either stored field. Save, import and reopen all use the same formatter; tab dirty marking is preserved.

The right-side actions are Add module, Add layer, a decorative vertical separator, Save, Import and Export. There is no separate title-edit icon. The footer only contains zoom out, scale, zoom in and Fit. Its old file-name/save-state nodes, static gesture instructions and corresponding rendering/CSS are removed. Storage still tracks edits and file handles for correct saving, import replacement confirmation and close-page protection. File-operation errors and data warnings use the existing feedback area; browser-tab dirty marking is unchanged.

## HTML and saving

`Serialization.buildDocument(bundle,project)` validates, escapes embedded JSON, and fills six slots once. `bundle={canvas,node,css,runtime}` comes from `scripts/build.mjs`'s `loadBundle()`. HTML holds project JSON in `script#ec-project[type=application/json]`, the immutable source bundle in `script#ec-bundle[type=application/json]`, and the module template in `template#ec-module-template`. Runtime scripts register under `globalThis.EasyCode`.

`Serialization.readProject(html)` reads the single top-level project data block without executing HTML and rejects missing/duplicate, wrong-type, unclosed or invalid JSON blocks. It returns data; call `Model.validate` separately. Do not parse embedded data with an ad hoc regex or treat an arbitrary script as the project.

`Storage.createController({getProject,buildDocument,readProject,validate,pickExisting,pickNew,onState})` exposes `save()`, `saveAs()`, `markDirty()`, `isDirty()`, `getFileName()`. Save methods return Promises. Initial Save binds only after matching project data and successful write/readback; later Save checks external changes. Save As chooses another target. Cancellation/failure retains dirty state; edits made while saving remain dirty. Native handles belong to that page session; reopening asks for the file again. There are no automatic backups or runtime package dependencies.
